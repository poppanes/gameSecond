# 移动端技术评估（2026-10-20）

## 技术栈选型结论

**路线 A「移动端 H5」先行 → 路线 B「微信小游戏」跟进 → 不引入游戏引擎。**

| 路线 | 说明 | 判断 |
|---|---|---|
| A. 移动端 H5（原生 JS + Canvas 2D + DOM 触控层） | 现有代码直接适配，零重构 | ✅ 主方案 |
| B. 微信小游戏（weapp-adapter） | H5 稳定后移植，user.js/ads.js 已留桩 | ✅ 二期 |
| C. Cocos/Laya/Unity 重写 | 代码全部重写，2~4 周起 | ❌ 不推荐 |

**架构友好性依据（摸底确认）**：
1. 画布固定内部分辨率 1000×900（1.11:1 近方形）+ `image-rendering: pixelated` 已就绪 → CSS `transform: scale` 缩放方案可行，游戏逻辑零改动
2. 输入系统零耦合：`GameInput.onKeyDown(code)` 统一分发，触控层只需模拟按键码调用现有方法；`pressedDirs` 按住连走机制现成
3. 底座已就绪：`env.js`（isMobile/isTouch/runtime）、字体已本地化（12KB woff2）、`user.js/ads.js` 平台适配层
4. 测试地图点击坐标换算已有 `getBoundingClientRect` 逻辑可复用

## 工作分解与耗时（总计约 3~3.5 天）

| # | 工作项 | 内容 | 耗时 |
|---|---|---|---|
| 1 | 画布自适应布局 | viewport meta + JS 计算 `min(屏宽/1000, 屏高可用/900)` 缩放 + resize 监听；`touch-action: none` 禁手势缩放；iOS 用 `dvh` 处理地址栏 | 0.5 天 |
| 2 | 触控输入层（核心） | DOM 虚拟按键：底部 D-pad（方向）+ 右侧 J/K 动作键；touch 事件映射到现有 `onKeyDown/onKeyUp`；`env.js.isTouch()` 控制显隐（PC 零影响）；电玩风半透明按钮 | 1 天 |
| 3 | 屏幕方向策略 | 竖屏优先（画布在上、触控条在下，无需旋转提示）；横屏时画布自动最大化——两方向自适应 | 0.5 天 |
| 4 | CRT 特效降级 | 移动端关 RGB 荫罩/色散/闪烁动画（合成层开销），保留扫描线+暗角；保 60fps | 0.5 天 |
| 5 | 音频手势解锁钩子 | 首次 touch 时 `resume AudioContext`（C 阶段音效前置） | 0.5 天 |
| 6 | 真机调试 | iOS Safari + Android Chrome + 微信内置浏览器；触控按钮调参 | 1 天 |

**二期·微信小游戏**：weapp-adapter + WechatAdapter/WechatAdProvider 填空 + 微信云开发（登录/排行榜）≈ 2~3 天。**软著等审核资质流程周期比开发长，建议开发同时启动办理。**

## 风险与前提

1. 缩放后格子约 35~40px：走格子靠 D-pad 不受影响；测试地图点格子略难（开发工具，可接受）
2. CRT 降级后视觉略打折，帧率优先；env.js 开关一行
3. 微信内置浏览器（X5/XWeb 内核）是最严格环境，真机调试必覆盖
4. 触控手感需真机迭代 1~2 轮（已计入）

## 推进顺序建议

先做 #1+2+3（1~2 天出可玩移动端 demo 真机体验）→ 按反馈调 #4~6 → 稳定后启动微信小游戏二期。
